# قرارداد رفتار وضعیت اتصال PGClockBot

این سند خروجی مرحلهٔ صفر [roadmap](CONNECTION_STATUS_ROADMAP.md) است. قرارداد محصول
و معیار تست را مشخص می‌کند؛ به‌تنهایی پایش، مدل دیتابیس یا مجوز اجرایی ایجاد نمی‌کند.

## دامنه و دسترسی

- **C01 — منبع:** تمام hostها، inboundها و حساب پایش از همان یک پنل PasarGuard هستند.
  Xray فقط کلاینت آزمایش است. نقطهٔ تست فعلی `local`، یعنی سرور خود ربات است.
- **C02 — مدیریت:** فقط Owner صریح و فعال سازمان، در ربات اصلی و با کنترل مجوز use case،
  تنظیمات را تغییر می‌دهد. `role=admin` به‌تنهایی کافی نیست. کلیدهای
  `connection_status` و `connection_status_manage` در use case کنترل می‌شوند.
- **C03 — scope:** shop از context احراز‌شده تعیین می‌شود؛ callback فقط شناسهٔ محلی دارد.
  خواندن/نوشتن خصوصی و نتیجهٔ دیررس هم scope می‌خواهند. مشتری دوم به تنظیمات خصوصی
  دسترسی ندارد؛ مشتریان یک shop می‌توانند همان فهرست منتشرشده را ببینند.
- **C04 — حساب پایش:** یک حساب موجود، اختصاصی و متعلق به scope انتخاب می‌شود؛ حساب
  واقعی مشتری یا سرویس متصل به خرید مشتری برای تست استفاده نمی‌شود. ایجاد، تمدید،
  شارژ یا reset خودکار این حساب در این قابلیت انجام نمی‌شود.

حساب باید فعال، دارای ظرفیت و اعتبار زمانی کافی و مجاز به inbound منتخب باشد.
توکن/UUID از سمت سرور خوانده می‌شود؛ نبود دسترسی، وضعیت نامعلوم حساب یا شکست بازگشایی
secret نتیجهٔ خرابی host نیست. credential در پیام یا snapshot عمومی ذخیره نمی‌شود.

## انتخاب و انتشار

- **C05 — انتخاب:** فقط host فعال و مجاز قابل انتخاب است؛ این شرط هنگام mutation دوباره
  بررسی می‌شود. وضعیت فعال در پنل، به‌تنهایی به معنی اتصال سالم نیست.
- **C06 — انتشار:** `test_enabled` و `is_public` در ابتدا خاموش‌اند. انتشار نیازمند
  پایش روشن، نام معتبر و نگاشت پشتیبانی‌شده است؛ نمونهٔ اول هنوز می‌تواند «نامشخص» باشد.
- **C07 — نام:** نام عمومی محلی، trimmed و بین ۱ تا ۶۴ نویسه است. نام/remark و تنظیمات
  host در پنل تغییر نمی‌کنند. آدرس یا نام فنی به‌جای نام عمومی خالی نمایش داده نمی‌شود.
- **C08 — توقف:** خاموش کردن پایش، انتشار را هم خاموش می‌کند. فعال کردن دوباره، انتشار
  قبلی را برنمی‌گرداند. حذف/غیرفعال شدن host در sync بعدی تست و انتشار را متوقف می‌کند.

ترتیب عمومی عدد صحیح در بازهٔ `0..2147483647` است؛ ترتیب مساوی با شناسهٔ محلی مرتب
می‌شود. `bool`، NaN، عدد منفی، float و مقدار خارج محدوده پذیرفته نمی‌شوند. متن نام در
Telegram escape می‌شود. انتخاب host دارای endpoint بیش از ظرفیت به‌صورت روشن رد یا
`not_ready` می‌شود؛ هیچ هدفی بی‌صدا از پوشش کم نمی‌شود.

## هویت هدف و نسخهٔ اندازه‌گیری

- **C09 — نگاشت:** هویت مسیر از `pg_host_id` و تنظیمات مؤثر endpoint به دست می‌آید؛
  index لیست یا `remarks` هویت نیست. نگاشت مبهم و ترکیب پشتیبانی‌نشده درخواست شبکه ندارند.
- **C10 — نسل:** تغییر آدرس، inbound، transport، حساب پایش یا تنظیمات مؤثر، نسل اندازه‌گیری
  را عوض می‌کند. نتیجه و پنجرهٔ نمونه‌های نسل قبلی، سلامت نسل جدید را ثابت نمی‌کنند.
  نام عمومی و ترتیب، به‌تنهایی نسل اندازه‌گیری را تغییر نمی‌دهند.
- **C11 — پوشش:** هر آدرس مؤثر قابل پشتیبانی یک `endpoint_key` پایدار دارد. نتیجهٔ host
  فقط در صورت پوشش همهٔ endpointهای موردنیاز می‌تواند سالم باشد. آدرس DNS حل‌شده در یک
  نمونه تضمین تمام مسیرهای DNS/CDN نیست و چنین ادعایی در محصول نمایش داده نمی‌شود.

ماتریس مرحلهٔ اول؛ syntax مسیرهای اولیه با core نسخهٔ 26.3.27 تأیید شد.
[شواهد و محدودیت‌های سازگاری](CONNECTION_STATUS_COMPATIBILITY.md) مرجع پشتیبانی است:

| ترکیب | تنظیمات لازم برای fixture و validation | وضعیت فعلی |
| --- | --- | --- |
| VLESS + Reality با transport خام | UUID، flow، serverName، fingerprint، public key و short ID | fixture و core validation قبول؛ اتصال زنده باز |
| VLESS + TLS/WebSocket | UUID، certificate verification، SNI، path، Host و port | fixture و core validation قبول؛ اتصال زنده باز |
| host با چند آدرس ساده | مسیر مستقل برای تمام آدرس‌های منتخب با تنظیمات security یکسان | پوشش مصنوعی و core validation قبول |
| wildcard/SNI تصادفی، XHTTP مسیر دانلود جدا، fragment و template سفارشی | نگاشت و وابستگی‌های اضافی | تا اثبات مستقل `not_ready` |
| سایر پروتکل/transportها | ماتریس و fixture مستقل مطابق نیاز واقعی | هنوز تأیید نشده |

نسخهٔ تأییدشدهٔ syntax مرحلهٔ یک Xray 26.3.27 روی macOS/arm64 است. پورت صریح و یک
SNI ثابت برای هر هاست لازم است. syntax/startup روی Linux/amd64 هم در CI تأیید شد؛
live test با test user در سرور مقصد در این تحویل skip شده است.

## قرارداد اندازه‌گیری

- **C12 — مسیر:** GET به مقصد ثابت HTTPS از ورودی HTTP محلی همان endpoint و outbound
  معتبر Xray عبور می‌کند. نبود پروکسی یا شکست آن به اتصال مستقیم fallback نمی‌کند.
- **C13 — موفقیت:** TLS معتبر، پایان داخل deadline و status دقیق مورد انتظار `204` لازم‌اند.
  `200`، redirect، `500` و صرف باز شدن TCP موفقیت نیستند؛ بدنهٔ نامنتظره دانلود نمی‌شود.
- **C14 — زمان:** delay فقط مدت درخواست شبکه با ساعت monotonic است؛ صف، خواندن پنل و
  startup را شامل نمی‌شود. زمان‌های ذخیره‌شده UTC هستند و روی خروجی با formatter مشترک
  نمایش داده می‌شوند. نتیجهٔ شکست delay ندارد و عدد ساختگی وارد میانه نمی‌شود.
- **C15 — مقصد کنترل:** بعد از شکست مقصد اول، مقصد مستقل دوم از همان پروکسی امتحان
  می‌شود. موفقیت مقصد دوم، دسترسی مسیر را ثابت می‌کند و مشکل مقصد اول فقط جزئیات ادمین است.
  نمونه‌های مقصدهای متفاوت در یک میانه مخلوط نمی‌شوند.

برای تأیید شکست مسیر، وضعیت حساب و runner باید معلوم باشد و حداقل یکی از مقصدهای
مقایسه در همان دور از کنترل مستقیم پاسخ مورد انتظار گرفته باشد. اگر هر دو درخواست
پروکسی شکست بخورند و کنترل/حساب نامعلوم باشد، نتیجه `unknown` است. کنترل مستقیم هیچ‌وقت
به‌جای موفقیت پروکسی ثبت نمی‌شود و علت «فیلتر بودن» از timeout استنتاج نمی‌شود.

روش اندازه‌گیری `fresh_http` است: اتصال HTTP هر نمونه تازه، HTTP/2 خاموش، client
در طول batch بازاستفاده و keep-alive بسته باشد. اتصال داخلی mux ممکن است بازاستفاده
شود؛ این روش به‌عنوان سنجش کاملاً سرد transport معرفی نمی‌شود.

## وضعیت‌ها و انتقال‌ها

| وضعیت داخلی | نمایش ادمین | نمایش مشتری در صورت انتشار |
| --- | --- | --- |
| `healthy` | در دسترس؛ delay، زمان و پوشش | در دسترس |
| `degraded` | اختلال؛ دلیل امن و پوشش | اختلال |
| `down` | خارج از دسترس پس از شکست تأییدشده | خارج از دسترس |
| `unknown` | نامشخص؛ نبود/قدیمی بودن یا علت مشترک | نامشخص |
| `not_ready` | آمادهٔ تست نیست؛ کد خطای امن | نامشخص؛ انتشار تازه مجاز نیست |
| `paused` | متوقف | از فهرست عمومی حذف می‌شود |

قواعد انتقال به ترتیب زیر تفسیر می‌شوند:

1. توقف، حذف یا لغو دسترسی، تست/انتشار را متوقف می‌کند؛ نتیجهٔ درحال‌اجرای قبلی معتبر نیست.
2. نبود config قابل‌پشتیبانی، `not_ready` است؛ نبود دادهٔ تازه یا علت مشترک مبهم `unknown` است.
3. نخستین نمونهٔ موفق معتبر برای هدف جدید، با پوشش و کیفیت مناسب، `healthy` است.
4. اولین و دومین دور شکست معتبر مسیر `degraded` و سومین دور متوالی `down` است.
5. پس از اختلال/قطعی، اولین دور موفق `degraded` و دومین دور موفق، در صورت کیفیت مناسب،
   `healthy` می‌شود. شکست معتبر، شمارندهٔ موفقیت را قطع می‌کند و برعکس.
6. دور نامعلوم یا فاصلهٔ فاقد اعتبار، streakها را قطع می‌کند؛ برای بازیابی از وضعیت
   نامعلوم بعد از شروع پایش، دو دور موفق تازه لازم است. قرائت مشتری، شمارندهٔ DB را عوض نمی‌کند.
7. میانهٔ نمونه‌های موفق معتبر بیش از دو ثانیه `degraded` است؛ مقدار دقیق دو ثانیه
   به‌تنهایی اختلال نیست. رسیدن به دو موفقیت، شرط آستانهٔ delay را حذف نمی‌کند.
8. در تجمیع host، وجود endpoint لازم با نسل نامعتبر/دادهٔ مفقود/stale اجازهٔ سبز شدن
   نمی‌دهد و وضعیت مؤثر `unknown` است. با پوشش معتبر، همه سالم → سالم، بخشی ناموفق →
   اختلال، و همه دارای قطعی تأییدشده → خارج از دسترس.

حداکثر پنج نمونهٔ موفق از همان endpoint، نسل، مقصد و پنجرهٔ freshness در میانه حضور
دارند. آخرین delay موفق در حالت شکست جاری نباید در خروجی به‌صورت یک موفقیت تازه نمایش داده شود.

نمونه‌های پذیرش سیاست برای تست‌های مرحلهٔ چهار:

| ورودی/توالی | انتظار |
| --- | --- |
| هدف جدید بدون اندازه‌گیری | `unknown` |
| هدف جدید، یک موفقیت با delay کم و پوشش کامل | `healthy` |
| هدف سالم، شکست معتبر اول/دوم/سوم | `degraded` / `degraded` / `down` |
| `down`، موفقیت اول/دوم با کیفیت مناسب | `degraded` / `healthy` |
| دو شکست، یک دور نامعلوم، یک شکست | streak شکست جدید برابر یک؛ قطعی اعلام نشود |
| میانهٔ delay برابر ۲۰۰۰ / بیشتر از ۲۰۰۰ میلی‌ثانیه | آستانه به‌تنهایی سالم / اختلال |
| دو endpoint، یکی سالم و دیگری stale | `unknown` با پوشش ناقص |
| دو endpoint، یکی سالم و دیگری `down` معتبر | `degraded` |
| پاسخ 204 مستقیم، هر دو درخواست پروکسی ناموفق | موفقیت ثبت نشود |
| تغییر نسل در زمان اجرای نمونه | نتیجهٔ قدیمی نتواند snapshot فعلی را بنویسد |

## پیش‌فرض‌های اجرایی

| پارامتر | مقدار اولیه | محدودهٔ تضمین |
| --- | --- | --- |
| روش و status | GET / 204 | مقصدها allow-list ثابت HTTPS و بدون redirect |
| فاصلهٔ بررسی | ۶۰ ثانیه | refresh مشتری باعث probe نمی‌شود |
| deadline هر درخواست | ۵ ثانیه | deadline کل، علاوه بر timeoutهای HTTPX |
| بودجهٔ دور | ۵۰ ثانیه | ۴۵ ثانیه کار و پنج ثانیه سهم cleanup |
| lease دور | ۹۰ ثانیه | نتیجه بعد از expiry یا واگذاری token رد شود |
| concurrency پروکسی | چهار endpoint | با lease runner مشترک، سقف چندprocess هم حفظ شود |
| ظرفیت اولیه | ۱۲ endpoint مؤثر | ظرفیت host چندآدرسی از تعداد endpoint محاسبه شود |
| freshness | ۱۸۰ ثانیه | `now >= checked_at + 180s` قدیمی است |
| اعتبار catalog/حساب | حداکثر ۱۸۰ ثانیه | پس از expiry، فعال/معتبر بودن دوباره فرض نشود |
| cooldown دستی | ۶۰ ثانیه برای هر هدف | درخواست تکراری pending جدید نسازد |
| آستانهٔ delay | ۲۰۰۰ میلی‌ثانیه | فقط نمونه‌های موفق همان سری |

محدودیت بودجه بر تعداد نمونه مقدم است؛ تمام شدن زمان، timeout جعلی یا قطعی host
ایجاد نمی‌کند. ترتیب due باید از بی‌نوبت ماندن دائمی اهداف جلوگیری کند. پارامترهای
ظرفیت در استقرار اعتبارسنجی می‌شوند و توسعهٔ UI تنظیماتشان در این PR لازم نیست.

## دادهٔ عمومی و شکست امن

خروجی عمومی فقط نام، وضعیت، زمان بررسی و نام نقطهٔ تست را نیاز دارد. آدرس، IP، tag،
UUID، token، config، exception خام و delay شخصی مشتری در آن نیست. عبارت «بررسی از
سرور ربات» همراه فهرست می‌آید. delay اندازه‌گیری‌شده در نسخهٔ اول فقط به ادمین نمایش داده می‌شود.

خواندن عمومی فقط snapshot محلی است؛ صفر panel call، صفر core start و بدون تغییر
state پایش. empty، unknown و error state متن امن دارند. خرابی پایش در سفارش، پرداخت،
کیف پول، تحویل یا فعال بودن host پنل تغییری ایجاد نمی‌کند.

## موارد عمداً موکول‌شده

اثبات mapping، ساخت DTO اجرایی، validation core، انتخاب نسخهٔ binary و تست‌های رفتار
در مراحل بعد مطابق roadmap انجام می‌شوند. این قرارداد ادعای تست زنده یا پشتیبانی
تأییدشدهٔ پروتکل‌ها نیست. نتیجهٔ مرحلهٔ صفر در [گزارش baseline](CONNECTION_STATUS_BASELINE.md) ثبت شده است.
